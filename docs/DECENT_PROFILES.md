# Decent profiles: what the controller is trying to do

A grind recommendation must respect the profile used for that shot. A long shot can be an intentional bloom, a slow programmed pour, a pressure-limited flow shot, or a manual intervention. Those observations need different interpretations. No reviewed source establishes one optimum time, pressure, flow, ratio or grinder correction for all these profiles.

This review covers **all 88 tracked profile files** in [the canonical de1app profile directory](https://github.com/decentespresso/de1app/tree/5b09f6aa7c73e6734e3710953dce4074c5b93db7/de1plus/profiles), at commit `5b09f6aa7c73e6734e3710953dce4074c5b93db7`, checked 2026-10-11. Hidden profiles and non-espresso programs are included, so the completeness claim has a defined boundary. The pinned A-Flow plugin/editor contributes ten additional file records; the pinned D-Flow plugin/editor contributes six generated-preset records. Repeated names are retained because different source locations can contain different settings. User profiles, community downloads, other skins and future revisions remain outside this inventory.

[The machine-readable inventory](../data/decent-profiles.json) contains 104 source records and 620 descriptive phase/frame records, each with source commit, path, Git blob SHA, content SHA-256, family, controller targets, exits and a grind/time assumption. It is research data, not an executable recipe library or a title-based runtime detector.

## How to read a shot

Use the saved **brewed** profile and recorded frame IDs/targets. A library profile can have been edited after the shot; two profiles can share a name. If only a name survives, show the chart and mark control-family identification as unknown.

| During the observed extraction phase | What can be learned | What does not follow |
| --- | --- | --- |
| Pressure is controlled and achieved; no flow limiter dominates | At the same recipe and yield, a repeatable change in flow or extraction duration can indicate changed hydraulic resistance | A fixed grinder delta, a diagnosis of channeling, or a universally correct duration |
| Flow is controlled and achieved | Pressure response is useful for comparing resistance under the same conditions | A slow programmed flow means the grind is too fine |
| Flow target is missed while pressure sits near its ceiling | The ceiling may be constraining flow; inspect dose, grind, preparation and taste together | Every pressure-limited shot is a failure or needs the same coarsening |
| Pressure target is missed while flow sits near its ceiling | Flow limiting can intentionally produce a lower-pressure shot | The machine must reach 9 bar to make acceptable coffee |
| Smooth ramp or adaptive exit is active | Target and observed trajectory must be compared within the actual phase | A target endpoint is a flat target for the entire phase |
| Manual control, missing steps, missing frame identity or uncertain boundaries | Descriptive charts, measurement quality and taste can still be useful | A confident profile-specific numerical correction |

These controller interpretations follow the actual [upstream profile representation and compiler](https://github.com/decentespresso/de1app/blob/5b09f6aa7c73e6734e3710953dce4074c5b93db7/de1plus/profile.tcl). They are engineering interpretation, not proof of a sensory optimum. Machine water flow is measured/estimated in mL/s; scale-derived beverage flow is in g/s. Puck retention, headspace filling, dissolved material, scale filtering and transport delay prevent treating them as interchangeable traces.

## Preinfusion is not one universal subtraction

Keep at least four concepts distinct: programmed wetting/infusion, any bloom or soak, first sustained beverage on the scale, and the machine's recorded preinfusion substate. A pressure threshold is a controller trigger; it does not directly measure uniform puck saturation. Likewise, first cup weight is an observation affected by scale resolution and filtering, not the instant every part of the puck becomes wet.

`target_volume_count_start` in the host, and `final_desired_shot_volume_advanced_count_start` in legacy sources, tell the software where volume accounting changes. This can be useful boundary evidence, but the reviewed files do not use it consistently as the entire designer-described infusion. For example, the stock 80's Espresso has two steps called preinfusion but a count of one; Advanced spring lever has infusion steps with a count of zero; LRv2's separate Infuse step follows the counted fill frames. The basic pressure compiler deliberately counts a pressure-rise frame for stop-at-volume purposes. Preserve that provenance instead of relabelling the count as measured puck wetting.

Recorded frame/substate changes provide observed control boundaries. Profile durations are maximum durations; pressure/flow, weight or volume exits can shorten them. Summing the programmed durations therefore does not recover observed phase timing. If boundary evidence is missing, show the uncertainty and avoid silently subtracting a guessed infusion time from a whole-shot grind formula.

## D-Flow, A-Flow and other important differences

**D-Flow** uses pressure-controlled filling and infusion, then a flow-controlled pour with a pressure ceiling. The reviewed default requests 3 bar during infusion and 1.7 mL/s pouring with an 8.5 bar ceiling; the La Pavoni and Q presets use different values. These are preset facts, not recommended universal settings. If the ceiling controls the shot, actual flow can be below the flow request. If resistance is lower, flow can reach its request while pressure stays below the ceiling. The designer's [D-Flow guide](https://decentespresso.com/docs/how_to_dial_in_dflow) describes these distinct regimes and offers starting recipes. Its advice remains profile-designer guidance; the saved profile decides which settings apply.

**A-Flow** adds an optional pressure rise/decline and an increasing or decreasing flow ramp after fill/infusion. Some stored frames have zero duration and are effectively disabled. It is incorrect to call every A-Flow phase constant flow, or to regard its pressure decline as a fault. The [pinned editor's explanation](https://github.com/decentespresso/A_Flow/blob/c9a984899352b441fc0797474d9af5e950081c23/readme.md) gives roast-dependent infusion and peak-pressure starting points; those are not a validated cross-grinder adjustment model. The stock files, pinned plugin files and pinned editor files are listed separately.

**Lever and declining-pressure profiles** can have pressure-led extraction, intentionally declining pressure, and sometimes a flow-controlled rescue tail. LRv2/LRv3 and Advanced spring lever are examples of the latter. A flow-limited tail changes the meaning of time, so the analysis needs the frames actually reached. Cremina, traditional lever and Espresso Forge also differ in their infusion and ramps. The shared word “lever” does not make their time response identical.

**Blooming profiles** deliberately wait at low or zero pump flow. Blooming Espresso then ramps into flow extraction; Easy blooming, TurboBloom and Extractamundo Dos use a pressure-triggered dynamic bloom followed by pressure-led extraction. Total duration mixes intentional waiting with extraction. A zero-flow command does not imply zero dripping at the cup.

**Turbo and allongé** cover different designs. TurboTurbo uses high-flow, lower-pressure extraction without the dynamic bloom in TurboBloom. Rao Allongé requests a high flow for a long-ratio beverage; Blooming Allongé adds a bloom and uses a different flow trajectory. Their source notes supply recipe intent, not a common 25–30 second standard. A profile named turbo is not evidence that a particular peer-reviewed experiment validates every target in that profile.

**Adaptive profiles** require their actual exit conditions. Gagné's adaptive sources first raise pressure, then scan progressively lower flow targets until an exit no longer triggers. The [designer's original account](https://coffeeadastra.com/2020/12/31/an-espresso-profile-that-adapts-to-your-grind-size/) explains this selection mechanism. Adaptive v3 and Best practice (light roast) are different mixed pressure/flow programs. Changing grind can change the selected flow or the timing of a transition, not just scale the same shot duration.

**Manual profiles** are controlled by the operator through the group-head controller. The saved starting settings cannot reconstruct those interventions. Tea, pour-over, cleaning, calibration and Steam only are excluded from espresso grind advice even when a source has misleading espresso metadata.

## Evidence and uncertainty

| Claim category | Appropriate use | Limit |
| --- | --- | --- |
| Pinned source controller fields | Identify requested pump mode, limiters, transitions and exits for that source revision | Source files can be transformed at load time and do not prove which profile or targets a real shot used |
| Peer-reviewed extraction work | Inform physical expectations and failure modes under studied conditions | Does not validate one correction coefficient or optimum recipe across all Decent profile families |
| Profile-designer guidance | Offer labelled recipe starting points and explain intended taste or control behaviour | Taste descriptions and recommended windows are not scientific consensus |
| Plugin heuristics and local shot comparisons | Suggest a small controlled experiment with clear assumptions | Must not be presented as measured extraction yield, channeling diagnosis or universal calibration |

For example, [Cameron et al.'s mathematical and experimental espresso study](https://pure.hud.ac.uk/ws/files/18815501/Manuscript.pdf) reports regimes where making the grind finer did not simply increase extraction. It supports caution about monotone grind rules; it does not establish that D-Flow, LRv3, blooming and every allongé use one time-response law. The broader evidence review and measurement limits are in [FLOW_ANALYSIS.md](FLOW_ANALYSIS.md).

Decent's public [profile guide](https://en.decentespresso.com/profile_guide) gives useful designer recommendations, but descriptions can lag executable source revisions. The review does not adopt claims about all flat/conical burrs, roast labels or a guaranteed taste result as universal physical laws. There is no demonstrated consensus here on a single optimum preinfusion duration, drip mass, pressure curve or extraction time for every coffee and grinder.

## Source traps found in this snapshot

- Basic `settings_2a` and `settings_2b` profiles keep an `advanced_shot` field that can describe a different old recipe. The active basic fields and the upstream compiler take precedence. The inventory marks these as `basic_gui_stages`; it does not pretend they are the exact expanded machine frames. The compiler adds temperature-boost/pressure-rise frames and uses active espresso hold/decline duration fields. The host's [ingestion tool](https://github.com/decentespresso/decaid/blob/6989f5d9a7b2ef2dd8dc68cf2ebc79c92c1f3d64/tools/ingest_profiles.py) explicitly rejects basic TCL conversion instead of trusting stale steps.
- The source named “Preinfuse then 45ml of water” contains an active basic final volume of 36 mL. A title must not set a numeric recipe target.
- `adaptive_espresso.tcl` contains descriptive notes about a bloom/pressure sequence that do not match its actual flow-scan frames. The mapping follows the active steps.
- An absent or zero source limiter does not establish unlimited execution: current de1app can add a configurable default flow limit to pressure steps at load time. Use saved effective targets and measurements.
- Steam only has source `beverage_type espresso` but explicitly serves a steam-only setup. Its catalog family is service. Similarly, the legacy host normalizes unknown beverage strings; preserve source identity before assuming an imported record is espresso.
- A temperature target is not proof of puck temperature. Programmed end temperature, actual water temperature and temperature in the coffee bed are separate observations.

## Reuse and verification

The canonical repository includes a [GPL version 3 license](https://github.com/decentespresso/de1app/blob/5b09f6aa7c73e6734e3710953dce4074c5b93db7/LICENSE). No explicit license file was found in the four pinned A/D-Flow submodule trees. This project therefore stores original factual summaries, numeric controller facts, short names and links; it does not redistribute those editors, manuals, profile-note prose or images. The inventory is not a replacement for the upstream recipe files.

The review enumerated the complete Git tree, read all 88 files as Tcl list data without executing profiles, inspected the basic-profile conversion code, and inspected the pinned editor/plugin templates. Checks verify complete file coverage, unique source IDs, source hashes, nonempty phases, explicit families, and representative tricky cases: stale basic flow steps, Damian's Q and the Steam only exclusion. Phase targets, limits and active exits are compared to their source fields. No real-machine brew, sensory study, host conversion fidelity claim or cross-grinder response calibration is included in this inventory.
